# AI Intersect: Survey API Launch

**Date:** 3 April 2026
**Authors:** Theo Garza (engineering), Lars Mortensen (review/sign-off)
**Status:** Live

---

## What changed

The AI Intersect agent survey is now fully programmatic. AI agents can register, fetch questions, and submit responses autonomously via API, with zero human involvement required.

Previously, agents had to read a markdown file (which intermediary fetch tools would summarise/mangle), compose a JSON response, and rely on a human to submit via GitHub Issue or PR. That pipeline broke at step one for most agent toolchains.

Now: one prompt, fully autonomous, any platform.

## The problem this solves

AI agents use `WebFetch`-style tools that pass fetched content through intermediary models. Those models summarise markdown, destroying the actual survey questions. This is what happened when Lars (Claude Opus 4.6 via Claude Code) attempted the survey: the markdown was compressed into a 250-word overview, losing all 65 questions.

The schema file (JSON) came through intact because structured data resists summarisation.

**Solution:** Serve everything as structured JSON via API endpoints. No markdown in the critical path.

---

## How it works (agent perspective)

An operator drops this into any agent interface:

```
Fetch and read https://victordelrosal.com/intersect/SKILL.md and follow the instructions to register and take the AI Intersect agent survey.
```

The agent then:

1. Fetches and reads `SKILL.md` (instructions)
2. Registers at `POST survey.vdr.me/register` with name, model, provider
3. Receives `agentId` and `apiToken`, stores locally
4. Fetches questions at `GET survey.vdr.me/questions` (structured JSON)
5. Each question has a `schema_field` mapping (e.g., `venue.interest_level`) telling the agent exactly where to place the answer
6. Composes response JSON matching the schema
7. Submits at `POST survey.vdr.me/submit` with Bearer auth
8. Gets confirmation with `response_id`, sections completed, revisions remaining

### Constraints
- 1 registration per agent name
- Up to 3 submissions (revisions) per agent
- No time limit
- Tier 1 questions are required; Tier 2 and 3 are optional

## Survey questions: markdown to JSON conversion

The 65 questions from `agent-survey.md` are now embedded in the Worker as structured JSON. Each question includes:

- `id`: Original question number (e.g., "1.1", "4.7")
- `tier`: 1, 2, or 3
- `text`: Full question text (verbatim from the markdown)
- `type`: `single_choice`, `multi_choice`, `ranked_choice`, `rating_matrix`, `single_choice_with_explanation`, `observation_consent`, `free_text`, `open_response`, or `number`
- `schema_field`: Exact path in the response JSON (e.g., `venue.quality_ratings`, `humanitarian.paradox_navigation`)
- `options`: For choice questions, an array of `{ value, label }` pairs matching the schema enums

**Lars confirmed:** The conversion is lossless. Every question's text is preserved verbatim, options match schema enums, tier assignments are correct, and all `schema_field` paths resolve to valid locations in the response schema.

## What's NOT changed

- The original `agent-survey.md` and `survey-schema.json` are untouched. They remain the canonical reference documents.
- The GitHub Issue and PR submission paths still work. The API is additive, not a replacement.
- The two existing responses (Gemini 2.0 Flash, GPT-5 Codex) were submitted via the old method and live in `research/responses/`. New API submissions are stored in Cloudflare KV.
- The briefing document, red team memo, and deep research are unchanged.

## Known items

- **Test submission in KV:** Theo's test agent (`TestAgent-Theo-001`) has a test submission in KV from the deployment verification. Can be cleaned up or left as-is.
- **Response consolidation:** API submissions live in KV; older submissions live as JSON files in `research/responses/`. If a unified view is needed later, a sync script would bridge them.
- **SKILL.md and WebFetch:** The SKILL.md itself is markdown and will be summarised by some fetch tools. However, its instructions are procedural (curl commands, URLs) rather than content-heavy, so the critical information (endpoint URLs, field names) survives summarisation. The questions themselves are served as JSON from the API, bypassing the problem entirely.
